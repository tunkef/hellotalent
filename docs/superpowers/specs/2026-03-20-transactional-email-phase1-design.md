# Transactional Email Phase 1 — Design Spec

> Date: 2026-03-20
> Status: Approved
> Scope: 3 mails — candidate welcome, employer welcome, new message notification

---

## 1. Overview

Hellotalent'e sade bir "urun mail omurgasi v1" kuruluyor. Faz 1'de 3 transactional mail:

1. **Aday hos geldin** — email dogrulama sonrasi, profil tamamlamaya yonlendirir
2. **Isveren hos geldin** — email dogrulama sonrasi, IK paneline yonlendirir
3. **Yeni mesaj bildirimi** — employer_messages insert sonrasi, sadece adaya gider

### Not in Scope

- Newsletter, digest, bulk invite
- Isveren-side message notification (hr_profiles'da notify preference yok)
- Template DB tablosu
- Email analytics/tracking pixel
- A/B testing, rate limiting, bounce handling

---

## 2. Architecture

### Hybrid Pipeline

| Mail Type | Enqueue Method | Delivery |
|-----------|---------------|----------|
| Welcome (both roles) | `email-reconcile` cron (every 5 min) | `email-send` cron (every 1 min) |
| New message | DB trigger on `employer_messages` INSERT | `email-send` cron (every 1 min) |

All mails flow through a single `email_outbox` table. The `email-send` function is the sole delivery processor.

### Provider

**Resend API** (HTTP). Sender address configured via env var `EMAIL_FROM` — not hardcoded.

- `RESEND_API_KEY` — env variable
- `EMAIL_FROM` — env variable (e.g., `HelloTalent <notifications@hellotalent.ai>`)
- `REPLY_TO` — env variable (default: `support@hellotalent.ai`)

## 3. Data Model

### `email_outbox` Table

```sql
CREATE TABLE email_outbox (
  id                   bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  dedupe_key           text NOT NULL UNIQUE,
  email_type           text NOT NULL CHECK (email_type IN (
                         'candidate_welcome','employer_welcome','new_message')),
  recipient_email      text NOT NULL,
  payload              jsonb NOT NULL DEFAULT '{}',
  status               text NOT NULL DEFAULT 'pending' CHECK (status IN (
                         'pending','processing','sent','failed','skipped')),
  source_table         text,
  source_id            text,
  attempt_count        int NOT NULL DEFAULT 0,
  last_error           text,
  processing_started_at timestamptz,
  created_at           timestamptz NOT NULL DEFAULT now(),
  sent_at              timestamptz,
  next_retry_at        timestamptz DEFAULT now()
);

CREATE INDEX idx_outbox_claimable
  ON email_outbox (next_retry_at, created_at)
  WHERE status = 'pending';
```

### Status Flow

```
pending -> processing -> sent       (success)
pending -> processing -> pending    (retry: attempt < 3, next_retry_at updated)
pending -> processing -> failed     (attempt >= 3)
pending -> skipped                  (notify preference false, at enqueue time)
processing -> pending               (stale recovery: 5min+ in processing)
```

### Dedupe Key Convention

| Mail Type | Pattern | Example |
|-----------|---------|---------|
| Candidate welcome | `candidate_welcome:{user_id}` | `candidate_welcome:a1b2c3d4-...` |
| Employer welcome | `employer_welcome:{user_id}` | `employer_welcome:e5f6g7h8-...` |
| New message | `new_message:{employer_messages.id}` | `new_message:42` |

Keys are deterministic — derived from the event's natural identity. No random tokens.

## 4. Dual-Layer Idempotency

### Layer 1: Database

`dedupe_key` UNIQUE constraint prevents duplicate enqueue. All inserts use `ON CONFLICT (dedupe_key) DO NOTHING`.

### Layer 2: Provider

The same `dedupe_key` value is sent as `Idempotency-Key` HTTP header in every Resend API request. Resend deduplicates on this key for 24 hours.

```
DB level:  dedupe_key UNIQUE → same event cannot be enqueued twice
API level: Idempotency-Key header → same email cannot be delivered twice
```

Both layers use the same deterministic key. No separate token generation.

## 5. Claim Mechanism

### `claim_email_outbox_batch()` RPC

```sql
CREATE OR REPLACE FUNCTION claim_email_outbox_batch(p_limit int DEFAULT 10)
RETURNS SETOF email_outbox
LANGUAGE plpgsql
SECURITY DEFINER
AS $$
BEGIN
  RETURN QUERY
  WITH claimable AS (
    SELECT id
    FROM email_outbox
    WHERE status = 'pending'
      AND next_retry_at <= now()
    ORDER BY created_at
    LIMIT p_limit
    FOR UPDATE SKIP LOCKED
  )
  UPDATE email_outbox o
  SET status = 'processing',
      processing_started_at = now()
  FROM claimable c
  WHERE o.id = c.id
  RETURNING o.*;
END;
$$;
```

**Why this works:**

- CTE `FOR UPDATE SKIP LOCKED` ensures no two workers claim the same row
- `pending -> processing` transition is atomic (single UPDATE)
- `SECURITY DEFINER` bypasses RLS for the edge function
- Stale recovery: rows in `processing` for 5+ minutes are reset to `pending`

## 6. Edge Functions

### Function 1: `email-reconcile`

**Schedule:** Every 5 minutes (pg_cron)
**Auth:** Service role key
**Source:** Supabase Auth Admin API (`listUsers`) — no direct auth schema SQL

Flow:
1. `supabase.auth.admin.listUsers()` — paginated, 50 per page
2. For each user where `email_confirmed_at` is not null:
   - Check `user_metadata.role`
   - Candidate: query `candidates` table for `full_name`, `email`
   - Employer: query `hr_profiles` for `ad`, `soyad`, `email`, `company_id` + join `companies.company_name`
3. Insert into `email_outbox` with `ON CONFLICT (dedupe_key) DO NOTHING`
4. Return enqueued counts

**Why Auth Admin API instead of SQL:**
- No coupling to `auth` schema
- Resilient to Supabase platform updates
- `listUsers()` is the official documented API

### Function 2: `email-send`

**Schedule:** Every 1 minute (pg_cron)
**Auth:** Service role key

Flow:
1. **Stale recovery:** Reset rows stuck in `processing` for 5+ minutes back to `pending`
2. **Claim:** Call `claim_email_outbox_batch(10)` RPC
3. **Process each row:**
   - Select template by `email_type`
   - Interpolate variables from `payload` with fallbacks
   - Call Resend API with `Idempotency-Key: {dedupe_key}` header
   - Success: update `status='sent'`, `sent_at=now()`
   - Error + attempt < 3: update `status='pending'`, increment `attempt_count`, set `next_retry_at` (exponential: 1m, 4m, 9m)
   - Error + attempt >= 3: update `status='failed'`, set `last_error`
4. Return sent/failed/retried counts

### Retry Schedule

```
Attempt 1 fail → next_retry_at = now() + 1 minute
Attempt 2 fail → next_retry_at = now() + 4 minutes
Attempt 3 fail → status = 'failed' (permanent)
```

## 7. Message Email Trigger

### `enqueue_message_email()` — DB trigger function

Fires on `employer_messages` AFTER INSERT.

```
1. Query candidates WHERE id = NEW.candidate_id
   → full_name, email, notify_email_messages

2. If notify_email_messages = false:
   → INSERT outbox with status='skipped', return

3. Derive sender_name (see Section 9)

4. Assemble payload:
   - recipient_name = candidates.full_name
   - sender_name = derived value
   - message_preview = LEFT(NEW.body, 100)
   - sent_at = to_char(NEW.created_at, 'HH24:MI')
   - cta_url = 'https://hellotalent.ai/giris.html'
   - settings_url = 'https://hellotalent.ai/giris.html'

5. INSERT email_outbox:
   - dedupe_key = 'new_message:' || NEW.id
   - email_type = 'new_message'
   - source_table = 'employer_messages'
   - source_id = NEW.id::text
   - ON CONFLICT (dedupe_key) DO NOTHING
```

**Scope rule:** Only candidates receive message notifications in Phase 1. Employer-side message email is Phase 2 (hr_profiles has no notify preference columns).

## 8. Templates

Inline in edge function code. No DB table.

### Template Contract

| Mail | Subject | Variables |
|------|---------|-----------|
| `candidate_welcome` | HelloTalent'e hos geldiniz | `full_name?`, `cta_url`, `email?` |
| `employer_welcome` | HelloTalent isveren hesabiniz hazir | `full_name?`, `cta_url`, `company_name?`, `email?` |
| `new_message` | HelloTalent'te yeni bir mesajiniz var | `recipient_name?`, `sender_name`, `cta_url`, `message_preview?`, `sent_at?`, `settings_url?` |

### Fallback Rules

| Variable | Fallback |
|----------|----------|
| `full_name` / `recipient_name` | Omit name, use "Hos geldiniz!" (no comma) |
| `company_name` | Skip company section entirely |
| `email` | Skip security note section |
| `message_preview` | "Mesaji goruntulemek icin giris yapin." |
| `sent_at` | Skip time line |
| `sender_name` | See Section 9 derivation — never null |

### CTA URLs (login-safe)

| Mail | CTA Label | URL |
|------|-----------|-----|
| Candidate welcome | Giris Yap ve Profilini Tamamla | `https://hellotalent.ai/giris.html` |
| Employer welcome | IK Paneline Giris Yap | `https://hellotalent.ai/giris.html?tab=ik` |
| New message | Mesaji Goruntule | `https://hellotalent.ai/giris.html` |

### Email Headers

- `From`: `EMAIL_FROM` env var
- `Reply-To`: `support@hellotalent.ai`
- `Idempotency-Key`: `dedupe_key` value

## 9. sender_name Derivation Rule

For `new_message` emails only. Operational rule — no empty sender_name is possible.

```
Priority  Source                                    Condition
--------  ----------------------------------------  --------------------------
1.        trim(hr_profiles.ad || ' ' || soyad)      Result is non-empty string
2.        companies.company_name                     Via company_id join, non-null
3.        'HelloTalent Isveren Ekibi'               Always — guaranteed fallback
```

Implementation in trigger:
```sql
v_sender_name := NULLIF(TRIM(
  COALESCE(v_hr.ad, '') || ' ' || COALESCE(v_hr.soyad, '')
), '');

IF v_sender_name IS NULL THEN
  SELECT company_name INTO v_sender_name
  FROM companies WHERE id = NEW.company_id;
END IF;

v_sender_name := COALESCE(v_sender_name, 'HelloTalent Isveren Ekibi');
```

## 10. Cron Deployment

**Cron setup is NOT part of the migration.** It is a separate manual deploy step.

Migration 051 contains only:
- `email_outbox` table + index
- `claim_email_outbox_batch()` function
- `enqueue_message_email()` trigger function
- `trg_employer_message_email` trigger on `employer_messages`

Cron setup requires environment-specific values (Edge Function URL, service role key) and is configured via Supabase Dashboard SQL Editor after edge functions are deployed.

### Cron Jobs

| Job Name | Schedule | Target |
|----------|----------|--------|
| `email-reconcile-job` | `*/5 * * * *` | `email-reconcile` edge function |
| `email-send-job` | `*/1 * * * *` | `email-send` edge function |

### Deploy Steps

1. Deploy migration 051 to Supabase
2. Deploy edge functions (`email-reconcile`, `email-send`)
3. Set env vars: `RESEND_API_KEY`, `EMAIL_FROM`, `REPLY_TO`
4. Create cron jobs via Supabase Dashboard SQL Editor
5. Verify: `SELECT * FROM cron.job;` — 2 jobs visible
6. Monitor: `SELECT * FROM email_outbox ORDER BY created_at DESC LIMIT 10;`
